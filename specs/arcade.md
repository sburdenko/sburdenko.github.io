Статус: v0.2 · 2026-10-07 — первый раздел реализован в `learn/`

> **Что решили при реализации (v0.2).** Делаем проще, чем в черновике ниже:
> - **Стиль Busuu + Duolingo**, а не аркада: чистая раскладка урока (карточка по центру,
>   большая кнопка внизу, панель с объяснением), палитра и шрифты сайта. Аркадные
>   термины (картриджи, `INSERT COIN`, `GAME OVER`) не используем. Полка — «Курсы»,
>   адрес `/learn/`.
> - **Только русский** на первом этапе; тексты лежат в данных уроков, английский добавим
>   позже.
> - **Без жизней.** Ошибка ставит карточку в конец урока (как в Duolingo), урок кончается,
>   когда на всё ответили верно. Звёзды — по числу ошибок, XP — за урок и ответы с
>   первой попытки, серия — по дням.
> - **Уроки не заперты.** Рекомендуемый следующий урок подсвечен, к остальным можно

> - **Для новичков и для опытных одновременно:** каждое понятие объясняется с нуля и
>   через аналогию, а в карточках теории есть раскрывающийся блок «Глубже» с деталями
>   для тех, кто уже программирует (tiered compilation, OSR, PGO, trimming, hostfxr…).
> - **Типы карточек MVP:** `learn`, `choice`, `multi`, `order`, `match`, `blanks`,
>   `tapline`, `rig` (стенды `stack`, `jit`, `race`). `sort`, `predict` и `speed` пока не
>   делаем: `predict` — это `choice` перед стендом, `sort` — `match`.
> - **Добавлен вводный урок** «Как компьютер понимает код» (процессор, машинный код,
>   компилятор), уровень про CIL стал третьим. Итого 8 уроков + финал.
>

## 1. Зачем и что делаем

На сайте уже есть **полка кассет**: длинные конспекты, которые читают сверху вниз и
крутят стенды. Сейчас нужен второй формат, короткий и игровой:

- урок на 4–7 минут, после которого остаётся ощущение «прошёл уровень»;
- на каждом экране что-то делаешь сам: тапаешь, перетаскиваешь, собираешь код,
  запускаешь машину. Длинные абзацы для чтения не используем;
- за ошибки отнимаются жизни, за уроки начисляются очки, по дням идёт серия, прогресс
  виден на карте уровней;
- полка общая для всего, что будем учить. .NET — первый трек, потом пойдут C#,
  Unity, алгоритмы, Python и т. д. Движок не должен знать, про что курс.

### Рамки MVP

| Входит | Не входит (позже) |
|---|---|
| Новая полка `/arcade/` с картриджами треков | Аккаунты, сервер, синхронизация между устройствами |
| Трек .NET с картой разделов (раздел 1 открыт, остальные «скоро») | Таблица рекордов между людьми |
| Раздел 1 «Managed execution»: 8 уроков + босс | Интервальные повторения (Leitner) — фаза 3 |
| Движок уроков: 10 типов карточек, жизни, очки, звёзды, разбор ошибок | Редактор курсов |
| Прогресс в localStorage, EN/RU, мобильная вёрстка | Запуск настоящего C# в браузере |
| Тесты на движок и на контент | |

## 2. Концепция: аркадный зал рядом с полкой кассет

Сайт сделан в эстетике VHS, конец 80-х — начало 90-х. В той же эпохе логично
смотрятся **игровые автоматы и картриджи**. Метафора Duolingo (уровни, жизни, очки)
ложится на них без натяжки, и придумывать чужой для сайта стиль не нужно.

| Duolingo / Sololearn | У нас | Где видно |
|---|---|---|
| Каталог курсов | **Аркадный зал** `/arcade/`, автоматы/картриджи | Отдельная полка, вход с главной |
| Курс | **Картридж** (трек): `.NET`, позже `C#`, `UNITY`, `ALGO`… | Обложка картриджа |
| Раздел (unit) | **Мир**: `WORLD 1 — MANAGED EXECUTION` | Карта трека |
| Урок | **Уровень**: `LEVEL 1-3` | Узел на тропе |
| Контрольный урок раздела | **Босс**: `BOSS 1 — ПУТЬ БАЙТА` | Последний узел мира |
| Сердечки | **Жизни** `♥ ♥ ♥` (3 на попытку) | OSD сверху |
| XP | **SCORE**, 6 цифр: `SCORE 000120` | OSD + экран итогов |
| Стрик | **Серия** `🔥 4` — дни подряд | OSD в зале |
| Конец сердец | `CONTINUE? 9…8…` → `GAME OVER` | Экран проигрыша |
| Итог урока | **Таблица рекордов**: очки, точность, время, звёзды ★★★ | Экран итогов |
| Достижения | **Наклейки** на картридж | Карточка трека |

Кнопки называем в том же аркадном духе: `INSERT COIN` (начать урок), `PRESS START`,
`CHECK ►`, `CONTINUE ►`, `1UP` (вернуть жизнь за верный ответ в разборе ошибок).

### Как полки связаны

```
/                     полка кассет (как сейчас) + новая «дверь» в аркаду
└─ /arcade/           аркадный зал: все картриджи (треки)
   └─ /arcade/dotnet/ карта трека .NET: миры и уровни
      └─ #play=1-3    уровень 1-3 открывается поверх карты (тот же документ)
```

- На главной `index.html` нужен заметный вход: отдельный блок под полкой,
  «неоновая вывеска» `ARCADE` с подписью «Учить по уровням». Это должна быть дверь
  в зал, а не седьмая кассета на полке.
- В строке состояния (`.osd`) зала: `PLAY ►`, `CH.A0 ARCADE`, очки, серия, EN/RU.
- Уровень открывается поверх карты трека (`#play=1-3`). Кнопка «назад» в браузере
  закрывает уровень, а не уводит из трека. При выходе посреди урока спрашиваем
  подтверждение: «Выйти? Прогресс уровня пропадёт».

## 3. Экраны

### 3.1 Зал `/arcade/`

- Заголовок в стиле главной (`h1.title`): **ARCADE** / *уровни, которые можно пройти*.
- Плашка игрока: общий SCORE, серия, цель дня (например, «1 уровень / день»: `■■□`).
- Сетка картриджей. Карточка картриджа:
  - корешок с номером и платформой: `CART 01 · .NET`;
  - прогресс трека: полоса и `3 / 9 уровней`;
  - кнопка `CONTINUE ►` (следующий непройденный уровень) или `INSERT COIN ►`;
  - наклейки-достижения;
  - у будущих треков состояние `COMING SOON`: картридж серый и неактивный, но
    виден, чтобы было понятно, что полка общая.
- Список картриджей берётся из реестра `arcade/tracks.js`. Чтобы добавить трек,
  достаточно одной записи в реестре и папки с контентом.

### 3.2 Карта трека `/arcade/dotnet/`

- Сверху шапка трека: название, сколько пройдено, звёзды.
- Ниже **тропа уровней** (как в Duolingo): узлы-«кнопки автомата» змейкой по
  вертикали, это удобно на телефоне. Состояния узла:
  `locked` (серый, замок) → `open` (пульсирует, «START») → `done` (★–★★★) →
  `perfect` (золотой, ★★★ без ошибок).
- Между мирами стоит большой заголовок-вывеска мира. Мир 2+ пока отображается как
  `COMING SOON` со списком тем, чтобы было видно, куда идёт трек.
- Узел босса крупнее остальных и с другой рамкой.
- Тап по открытому узлу открывает карточку уровня: название, 1 строка «что
  узнаешь», ~время, лучший результат, `INSERT COIN ►`.
- Уровни открываются по порядку. Пройденный уровень можно перепроходить ради звёзд.
  «Пройти тест и перепрыгнуть» — фаза 3.

### 3.3 Экран уровня (плеер)

Раскладка mobile-first, ширина от 360px:

```
┌──────────────────────────────────────┐
│ ✕   ▓▓▓▓▓▓▓░░░░░  7/12     ♥ ♥ ♡      │  ← OSD: выход, прогресс, жизни
├──────────────────────────────────────┤
│                                      │
│   [ CRT-экран с карточкой ]          │  ← сама карточка (вопрос, стенд, код)
│                                      │
├──────────────────────────────────────┤
│ ✓ ВЕРНО  +10                         │  ← панель ответа (зелёная/красная),
│ CIL не зависит от процессора…        │     выезжает снизу с объяснением
│                        [ CONTINUE ►] │
└──────────────────────────────────────┘
          [        CHECK ►        ]       ← большая кнопка в зоне большого пальца
```

- Одна карточка на экран. Чтобы перейти к следующей, нужно сначала нажать `CHECK`,
  потом `CONTINUE` (как в Duolingo).
- Верный ответ: зелёная вспышка рамки CRT, `+10` всплывает к SCORE, короткий
  чиптюн-«бип».
- Ошибка: красная полоса трекинга проходит по экрану (берём `@keyframes glitch` и
  `.fx-track` из `vhs.css`), сердце гаснет, телефон коротко вибрирует
  (`navigator.vibrate(60)`). В объяснении сказано, **почему выбранный вариант
  неверен**, а не только какой верный.
- Карточка с ошибкой уходит в **очередь разбора**. После основных карточек:
  `REPLAY MISTAKES`, те же карточки, варианты перемешаны. Верный ответ в разборе
  даёт `1UP`: возвращает одно сердце, но не выше 3.
- Все сердца потеряны: экран `CONTINUE? 9…8…` с двумя кнопками: `RETRY LEVEL` и
  `BACK TO MAP`. Платных продолжений и ожидания восстановления сердец нет: это
  учебный сайт, наказывать временем незачем.
- Экран итогов в стиле таблицы рекордов: `SCORE`, `ACCURACY 92%`, `TIME 4:12`,
  звёзды, новые наклейки, кнопки `NEXT LEVEL ►` / `REPLAY`.

### 3.4 Звёзды и очки

| Событие | Очки |
|---|---|
| Верный ответ с первой попытки | +10 |
| Верный ответ в разборе ошибок | +5 и `1UP` |
| Уровень пройден | +20 |
| Уровень без ошибок (`PERFECT`) | +30 |
| Босс пройден | +100 |
| Серия на скоростном раунде (каждые 3 подряд) | +5 комбо |

Звёзды: ★ — прошёл, ★★ — не больше 2 ошибок, ★★★ — без ошибок. В итог идёт лучший
результат.

## 4. Движок: типы карточек

Урок описывается **данными**, а не кодом: массив карточек. Каждый тип карточки
состоит из рендера (DOM) и **чистой функции проверки** без DOM, которую покрываем
тестами. Это то же правило, что на кассетах: модели отдельно, отрисовка отдельно.

| # | Тип | Что делает человек | Пример в разделе 1 |
|---|---|---|---|
| 1 | `intro` | Читает ≤ 40 слов + смотрит анимацию, жмёт `CONTINUE` | «Один .dll на x64 и на ARM» |
| 2 | `choice` | Выбирает один вариант (2–4) | «Кто задаёт синтаксис — компилятор или CLR?» |
| 3 | `multi` | Отмечает все верные | «Что лежит в PE-файле сборки?» |
| 4 | `order` | Перетаскивает шаги в правильный порядок | 4 шага managed execution |
| 5 | `match` | Соединяет пары (тап слева → тап справа) | Термин ↔ определение |
| 6 | `sort` | Раскладывает плашки по корзинам | «Компиляция» / «Выполнение» |
| 7 | `code-blanks` | Собирает код из плиток в пропуски (как Sololearn) | Дописать IL для `a * b + c` |
| 8 | `predict` | Предсказывает результат прогона стенда, потом смотрит прогон | «Сколько методов скомпилирует JIT?» |
| 9 | `tap-line` | Тапает по строке кода / части схемы | «Какая строка не пройдёт верификацию?» |
| 10 | `rig` | Делает действие на живом стенде до цели | Стековая машина, JIT-заглушки |
| 11 | `speed` | Быстрый раунд «верно/неверно», 30 секунд, комбо | Босс |

У `rig`-карточки цель проверяемая: стенд отдаёт событие с состоянием, а проверка
чистой функцией смотрит, достигнута ли цель («стек пуст, на выходе 42»). Стенды
пишем так же, как на кассетах: модель без DOM и отдельный вид.

### Формат данных (пример)

```js
// arcade/dotnet/w1/l3-cil.js
export default {
  id: 'dotnet.w1.l3',
  title: { en: 'CIL: a stack machine', ru: 'CIL: язык стековой машины' },
  goal:  { en: 'Read and write tiny IL', ru: 'Читать и писать маленький IL' },
  minutes: 6,
  cards: [
    { type: 'intro', key: 'l3.hook', art: 'stack-machine' },
    {
      type: 'choice', key: 'l3.cpu',
      options: ['l3.cpu.a', 'l3.cpu.b', 'l3.cpu.c'],
      answer: 0,
      explain: { 'l3.cpu.b': 'l3.cpu.whyB', 'l3.cpu.c': 'l3.cpu.whyC' }
    },
    {
      type: 'code-blanks', key: 'l3.mul',
      lang: 'il',
      template: 'ldarg.0\n___\nmul\n___\nadd\nret',
      tiles: ['ldarg.1', 'ldarg.2', 'ldc.i4.1', 'sub', 'stloc.0'],
      answer: ['ldarg.1', 'ldarg.2']
    },
    { type: 'rig', key: 'l3.run', rig: 'stack', program: 'addMul', goal: { kind: 'halt', top: 42 } }
  ]
};
```

Тексты живут в словаре `{ key: { en, ru } }`, как везде на сайте. В контенте только
ключи. Тест проверяет, что у каждого ключа есть оба языка (`tests/i18n.test.js`
дополняется страницами аркады).

### Состояние уровня — чистый автомат

```
idle → card(i) → answered(ok|fail) → card(i+1) … → review(j) … → result
                       └─ lives == 0 ──────────────→ gameover
```

`arcade/engine/run.js` экспортирует `start(lesson, seed)`, `answer(state, input)`,
`next(state)` и ничего не знает о DOM. Перемешивание вариантов идёт через
детерминированный `assets/rand.js` с seed, поэтому прогон можно повторить в тесте.

### Прогресс

`localStorage`, один ключ `arcade.v1`. Каждое чтение и запись обёрнуты в
`try/catch`: в приватном режиме хранилище может быть недоступно, тогда страница
работает без сохранения и показывает тихую плашку «прогресс не сохранится».

```js
{
  v: 1,
  score: 1240,
  streak: { days: 4, last: '2026-10-07' },
  goal: { perDay: 1, today: 1 },
  levels: { 'dotnet.w1.l1': { stars: 3, best: 130, done: '2026-10-05' } },
  stickers: ['first-coin', 'jit-whisperer'],
  mistakes: { 'dotnet.w1.l3/l3.mul': 2 }   // для будущих повторений
}
```

Серия считается по локальной дате. Пропустил день — серия сгорает. «Заморозка
серии» — фаза 3.

## 5. Визуальный стиль

Основа — то, что уже есть в `assets/vhs.css`. Новые цвета не вводим, используем
токены `--cpu`, `--gpu`, `--osd`, `--ok`, `--bad`, шрифты Unbounded / VT323 /
JetBrains Mono / IBM Plex Sans, `.crt`, `.osd`, `.btn.primary`, `.chip`, `.tg`.

Слой аркады (`arcade/arcade.css`):

- **Картридж** — вариация `.cassette`: вместо катушек «контакты» снизу и
  наклейка-обложка с логотипом трека (`.NET` фиолетовым в стиле логотипа, но
  нашим шрифтом).
- **Узлы тропы** — круглые аркадные кнопки с бликом: `open` — жёлтый `--osd` с
  пульсацией, `done` — `--gpu`, `perfect` — золотой градиент + ★★★, `locked` —
  `--bg4` с замком.
- **Жизни** — пиксельные сердца SVG 9×8 «пикселей», цвет `--cpu`; погасшее —
  контур `--line2`.
- **SCORE** — VT323, 6 цифр с ведущими нулями, при начислении счётчик быстро
  крутится.
- **Карточка** — внутри `.crt`, чтобы урок выглядел как экран автомата.
  Код — подсветка из `assets/code.js` (добавить режим `il` для CIL).
- **Плитки кода** (`code-blanks`) — моноширинные «клавиши» с тенью снизу; при
  перетаскивании приподнимаются.
- **Анимации** уважают `prefers-reduced-motion` (флаг `RM` из `vhs.js`): без
  вспышек и тряски, только смена цвета.
- **Звук** — короткие квадратные волны через WebAudio (`sfx.js`): верно / ошибка /
  уровень пройден / 1UP. По умолчанию **выключен**, переключатель `SND` в OSD.

Доступность: всё делается и мышью, и с клавиатуры. `order` и `sort` дублируются
кнопками «вверх/вниз» и «в корзину». Есть фокус-кольцо `--osd`, и о результате
проверки сообщает `aria-live="polite"`.

## 6. Контент: трек .NET, мир 1 — «Managed execution: путь кода от .cs до процессора»

### Сквозная идея мира

Весь мир идёт за одним маленьким героем — программой:

```csharp
// Hello.cs
class Program
{
    static int Add(int a, int b) => a + b;
    static void Main() => Console.WriteLine(Add(40, 2));
}
```

Класс написан явно, без top-level statements, иначе `Add` станет локальной функцией
с именем вроде `<<Main>$>g__Add|0_0`, и уровни про метаданные и рефлексию
запутаются.

Уровень за уровнем она превращается: исходник → CIL + метаданные → PE-файл →
JIT-заглушки → машинный код → работающий процесс с сервисами CLR. На карте мира
рядом с тропой нарисован этот «путь байта», и пройденные участки загораются. На
каждом уровне человек видит, на каком участке пути он сейчас.

### Правило «Сверено с докой»

Статья Microsoft 2017 года и описывает в основном .NET Framework: NGen,
верификацию по политике безопасности, загрузчик Windows Vista. Мы учим по ней, но
в каждом месте, где современный .NET (8–10) работает иначе, ставим плашку
**«Сверено с докой»** с коротким уточнением. Так же на кассетах помечено «Сверено
с книгой». Все такие факты перед реализацией сверяем с актуальной документацией
learn.microsoft.com, ссылки кладём в `facts.js`.

#### LEVEL 1-1 · Два мира: managed и native

**Цель:** понять, что такое managed code и из каких 4 шагов состоит путь.
**Вау-момент:** один и тот же `Hello.dll` «запускается» на двух автоматах —
x64 и ARM64, а `hello.exe` на C++ работает только на одном.

1. `intro` — две аркадные машины `x64` и `ARM64`. Вставляем в обе картридж
   `Hello.dll`: обе печатают `42`. Вставляем `hello.exe` (C++, x64): ARM-машина
   выдаёт `BAD CARTRIDGE`. «Почему? Сейчас разберёмся».
2. `choice` — managed code — это код, который…
   (выполняется под управлением CLR ✓ / написан только на C# / всегда медленнее
   native / не может вызывать native-код).
3. `intro` — 4 шага, плашками: **компилятор → CIL + метаданные → JIT в машинный
   код → выполнение под CLR**.
4. `order` — расставь 4 шага в правильном порядке.
5. `sort` — «когда это происходит?»: *компиляция C# в CIL, создание метаданных*
   → **при сборке**; *JIT в машинный код, сборка мусора* → **при запуске**.
6. `predict` — в машину ARM64 вставляют `Hello.dll`, собранный на x64-ноутбуке.
   Заработает? (да ✓ — CIL не зависит от процессора, JIT есть под каждую
   архитектуру). Затем анимация.
7. `choice` — ловушка: managed-код вызывает Win32 API напрямую. Запустится на
   Linux? (нет ✓ — платформенно-зависимые вызовы привязывают код к ОС; статья
   говорит об этом прямо).
8. `match` — CLR / CIL / JIT / metadata ↔ короткие определения.
9. `speed` — 6 утверждений верно/неверно, 20 секунд.

#### LEVEL 1-2 · Компилятор и общий язык (CLS)

**Цель:** синтаксис задаёт компилятор, а не runtime; что такое CLS и зачем
`[CLSCompliant]`.
**Вау-момент:** `Add` на C#, F# и VB.NET компилируется в один и тот же IL —
почти: у VB.NET вместо `add` стоит `add.ovf`, потому что VB по умолчанию проверяет
переполнение. Смысл `+` определил компилятор, а не runtime.

1. `intro` — три картриджа C#, F#, VB; все три «вливаются» в одну воронку CLR.
2. `rig` — «IL-проектор»: переключай язык C# / F# / VB, слева исходник `Add`,
   справа IL. У C# и F# `ldarg.0 ldarg.1 add ret`, у VB одна строка мигает:
   `add.ovf`. Цель: переключить все 3 и тапнуть по отличающейся строке.
   После — вопрос: почему VB дал другой IL? (компилятор VB по умолчанию
   включает проверку переполнения ✓). Тумблер «Remove integer overflow checks»
   в VB-проекте убирает отличие.
3. `choice` — кто определяет, что `x => x + 1` — законный синтаксис?
   (компилятор языка ✓ / CLR / JIT / ОС).
4. `choice` — CLS — это… (общее подмножество возможностей, понятное всем .NET-языкам ✓ /
   отдельный язык / формат файла / сборщик мусора).
5. `tap-line` — публичный класс, помеченный `[assembly: CLSCompliant(true)]`.
   Тапни строку, на которую компилятор даст предупреждение:
   `public uint Count { get; }` ✓ (`uint` не входит в CLS).
6. `tap-line` — два публичных метода `Run()` и `run()` в одном типе. Что не так?
   (имена отличаются только регистром — VB.NET их не различит ✓).
7. `choice` — `private uint _x;` в CLS-совместимой сборке — ошибка? (нет ✓ — CLS
   касается только того, что видно снаружи сборки).
8. `sort` — CLS-совместимо в публичном API / нет: `int`, `string`, `uint`,
   `sbyte`, `long`, `ulong`.
9. `match` — язык ↔ «кто компилирует в CIL»: `csc`/Roslyn, `fsc`, `vbc`.

#### LEVEL 1-3 · CIL — язык стековой машины

**Цель:** CIL — набор инструкций, не зависящий от процессора; читать и писать
простейший IL.
**Вау-момент:** ты сам «исполняешь» IL на стековой машине и видишь, как `40` и
`2` превращаются в `42`.

2. `choice` — CIL не зависит от процессора, поэтому… (один и тот же IL JIT-ится

4. `predict` — что будет на вершине стека после `ldarg.1`? (2 ✓).
5. `code-blanks` — собери IL для `a * b + c`:

6. `multi` — какие операции есть в CIL? (загрузка/сохранение ✓, вызов методов ✓,

7. `rig` — **стек сломался**: дана программа `ldarg.0 · add · ret`. Нажми `STEP`

   не пройдёт проверку? (на стеке один элемент, а `add` нужно два ✓) — мостик к

8. `tap-line` — в IL Hello World найди строку, которая вызывает метод из другой

#### LEVEL 1-4 · Метаданные и PE-файл

**Цель:** что лежит в сборке; метаданные делают код самоописываемым.
**Вау-момент:** «вскрываешь» `Hello.dll` как картридж и видишь таблицы

4. `multi` — что описывают метаданные? (определения типов ✓, сигнатуры членов ✓,

5. `choice` — зачем .NET не нужны IDL и type libraries, как в COM? (сборка

6. `predict` — `typeof(Program).GetMethods(BindingFlags.Static | BindingFlags.NonPublic)`.

7. `tap-line` — в `MemberRef` найди ссылку на `Console.WriteLine` ✓ (связь с 1-3).
8. `order` — собери картридж: заголовок PE → заголовок CLR → метаданные → IL.
9. `choice` — как ОС понимает, что перед ней образ CLR? (формат PE содержит

#### LEVEL 1-5 · JIT: компиляция по требованию

**Цель:** заглушки, первая компиляция, повторные вызовы, «никогда не вызванный
метод не компилируется», код живёт только в процессе.
**Вау-момент:** **стенд-заглушки**: жмёшь «вызвать», и у метода заглушка
`→ JIT` на глазах превращается в прямой переход `→ native`.

1. `intro` — при загрузке типа загрузчик ставит каждому методу **заглушку**
   (stub). Первый вызов идёт через заглушку в JIT.
2. `rig` — **JIT-стенд**: класс с методами `Main`, `Add`, `Log`, `Unused`.
   Кнопки «вызвать». Первый вызов `Add`: заглушка → JIT (полоска «компиляция»,
   +время) → машинный код, заглушка перенаправлена. Второй вызов идёт сразу в
   native, время почти 0. Счётчики: *методов скомпилировано*, *время JIT*,
   *вызовов*. Цель: вызвать `Add` дважды.
3. `predict` — программа вызывает `Add` 1000 раз. Сколько раз JIT скомпилирует
   `Add`? (1 ✓ — за исключением многоуровневой компиляции, см. карточку 7).
4. `predict` — после запуска программы, которая ни разу не вызвала `Unused`,
   сколько методов скомпилировано? Стенд проверяет ответ прогоном: `Unused`
   остался серым.
5. `choice` — запускаем ту же программу второй раз. JIT-код из первого запуска
   переиспользуется? (нет ✓ — код JIT привязан к процессу, после выхода он
   пропадает).
6. `sort` — плюсы/минусы JIT: *компилирует только вызываемое*, *знает точный
   процессор* → плюсы; *задержка первого вызова*, *код не делится между
   процессами* → минусы.
7. `intro` + **Сверено с докой** — в современном .NET JIT **многоуровневый**
   (tiered compilation, включена по умолчанию с .NET Core 3.0): сначала быстрый
   Tier 0, горячие методы после ~30 вызовов перекомпилируются в оптимизированный
   Tier 1 в фоне; с .NET 8 по умолчанию включён Dynamic PGO. Стенд из карточки 2
   получает тумблер `TIERED` и показывает, как `Add` после 30 вызовов
   перекомпилируется второй раз.
8. `predict` — с включённым `TIERED`: сколько раз скомпилируется `Add` за 1000
   вызовов? (2 ✓ — Tier 0, затем Tier 1).
9. `speed` — 7 утверждений про JIT, 25 секунд.

#### LEVEL 1-6 · Заранее: NGen, ReadyToRun, Native AOT

**Цель:** чем ahead-of-time отличается от JIT; что из этого есть в каком .NET.
**Вау-момент:** **гонка старта**: три автомата одновременно запускают одну
программу (JIT / ReadyToRun / Native AOT), и видно, кто первым печатает `42`
и сколько весит каждый картридж.

1. `intro` — JIT платит временем при каждом запуске. Можно скомпилировать заранее.
2. `match` — три отличия NGen от JIT из статьи: *до запуска, а не во время*,
   *вся сборка сразу, а не по методу*, *результат сохраняется на диск в Native
   Image Cache*.
3. `intro` + **Сверено с докой** — NGen есть только в .NET Framework. В
   современном .NET вместо него **ReadyToRun** (`PublishReadyToRun`, внутри и
   готовый код, и IL; JIT всё ещё может перекомпилировать горячие методы) и
   **Native AOT** (`PublishAot`, JIT в рантайме нет вообще).
4. `rig` — **гонка старта**: три дорожки, кнопка `RACE`. Время до первого вывода,
   размер на диске, есть ли JIT в процессе. Числа — условные коэффициенты модели
   (подпись «модель, не бенчмарк», как на кассете про батчинг).
5. `sort` — разложи по технологиям: *нет JIT в рантайме* → Native AOT;
   *IL лежит рядом с готовым кодом* → R2R; *только .NET Framework* → NGen;
   *компиляция при первом вызове* → JIT.
6. `choice` — приложение активно грузит плагины через `Assembly.LoadFrom` и
   генерирует код через `Reflection.Emit`. Native AOT подойдёт? (нет ✓ — в
   Native AOT нет динамической загрузки сборок и генерации кода во время работы).
7. `choice` — нужно быстрее стартовать, но ничего не ломать в рефлексии. Что
   включить? (ReadyToRun ✓).
8. `code-blanks` — собери строку в `.csproj`:
   `<___>true</___>` → `PublishAot` (плитки: `PublishAot`, `PublishTrimmed`,
   `TieredPGO`, `Optimize`).
9. `speed` — «JIT / R2R / Native AOT / NGen?»: 8 карточек, 30 секунд.

#### LEVEL 1-7 · Верификация и типобезопасность

**Цель:** что такое type-safe; три утверждения, на которые опирается runtime;
что даёт верификация и что изменилось сейчас.
**Вау-момент:** «пропускной пункт»: человек сам работает верификатором и
пропускает или заворачивает куски IL. Один из них **типобезопасен, но всё равно
не проходит**: так статья предупреждает, что верификатор консервативен.

1. `intro` — типобезопасный код обращается только к той памяти, к которой имеет
   право. Это изолирует объекты друг от друга.
2. `match` — три утверждения из статьи ↔ пример нарушения:
   *ссылка совместима с типом* ↔ строку читают как `int[]`;
   *у объекта вызываются только определённые для него операции* ↔ вызов
   несуществующего метода через подделанный указатель;
   *идентичности такие, какими себя называют* ↔ объект выдаёт себя за другой тип.
3. `rig` — **пропускной пункт**: 6 карточек с кодом (C# + IL под ним). Для
   каждой: `PASS` / `REJECT`. Среди них: обычный метод ✓ PASS, `unsafe`-код с
   указателем за пределы массива → REJECT, IL с `STACK UNDERFLOW` из уровня 1-3 →
   REJECT, и «ловушка»: корректный `unsafe`-код без выхода за границы →
   тоже REJECT (не верифицируем, хотя и безопасен).
4. `choice` — почему безопасный `unsafe`-код не прошёл? (верификатор доказывает
   безопасность только для чётко определённого набора конструкций; часть
   безопасного кода в него не попадает ✓).
5. `multi` — что проверяет верификация? (обращения к памяти только через
   корректные типы ✓, правильно ли сгенерирован IL ✓, правильный ли алгоритм ✗,
   нет ли утечек памяти ✗).
6. `intro` + **Сверено с докой** — в .NET Framework верификацию требовала
   политика безопасности (CAS). В .NET Core / .NET 5+ CAS и частичного доверия
   нет, и runtime **не верифицирует IL** при загрузке. Проверить IL можно
   инструментом ILVerify, а типобезопасность обеспечивают компилятор и сам
   runtime (проверки границ массивов, приведения типов).
7. `predict` — `object o = "hi"; var a = (int[])o;` — что будет? (исключение
   `InvalidCastException` ✓ — runtime не даст нарушить совместимость типов).
8. `predict` — `int[] a = new int[3]; a[5] = 1;` → `IndexOutOfRangeException` ✓
   (запись за пределы массива невозможна в безопасном коде).
9. `speed` — «type-safe или нет?», 8 карточек.

#### LEVEL 1-8 · Запуск: CLR и его сервисы

**Цель:** что даёт CLR во время выполнения; как процесс вообще попадает в CLR.
**Вау-момент:** **«сыграй загрузчик»**: двойной клик по `hello.exe`, и человек
сам по цепочке передаёт управление, пока программа не напечатает `42`.

1. `intro` — пока код работает, CLR даёт ему сервисы: **сборку мусора**,
   **безопасность**, **взаимодействие с unmanaged-кодом**, **отладку между
   языками**, **развёртывание и версии**.
2. `match` — сервис ↔ ситуация: объекты больше не нужны → GC; вызов функции из
   C-библиотеки → interop (P/Invoke); брейкпоинт в F#-библиотеке из C#-проекта
   → отладка между языками; две версии одной библиотеки → версионирование.
3. `order` — **загрузчик по статье (Windows, .NET Framework)**: ОС видит
   признак managed-модуля в COFF-заголовке → грузит `mscoree.dll` →
   `_CorValidateImage` проверяет, что код корректный managed → точка входа
   подменяется на точку входа runtime → вызывается `Main`.
4. `choice` — что `_CorValidateImage` делает на 64-битной Windows сверх этого?
   (переводит образ в памяти из PE32 в PE32+ ✓).
5. `intro` + **Сверено с докой** — в .NET (Core) 5+ цепочка другая и одинаковая
   на всех ОС: `hello.exe` (apphost) или `dotnet hello.dll` → `hostfxr` (выбирает
   версию runtime) → `hostpolicy` (собирает зависимости) → `coreclr` → `Main`.
6. `rig` — **сыграй загрузчик**: перетаскивай «эстафетную палочку» по цепочке
   современного хоста. Ошибка в порядке — машина выдаёт реальное по смыслу
   сообщение («You must install or update .NET to run this application», если
   пропустить поиск runtime). Цель: дойти до `42`.
7. `predict` — финальный прогон всего пути: `Main` вызывает `Add` первый раз.
   Что происходит дальше? (заглушка → JIT → машинный код → `42` ✓) — связка с
   1-5: весь цикл «JIT-компиляция, потом выполнение» повторяется до конца
   программы.
8. `sort` — «кто это делает?»: *компилятор C#*, *JIT*, *GC*, *хост* ↔ действия.
9. `speed` — 8 утверждений обо всём мире.

#### BOSS 1 · Путь байта

**Цель:** проверить весь мир одним прохождением.
**Формат:** 14 карточек всех типов вперемешку. Жизней 3, в разборе ошибок `1UP`
нет. Таймер на всё прохождение не ставим (только на `speed`-раунды), чтобы
проверялось понимание, а не скорость.

Сценарий: программа `Hello.cs` проходит по всей карте мира, и на каждом участке
пути её «ловит» вопрос этого участка:

1. `order` — весь путь из 6 шагов: исходник → компилятор → CIL + метаданные в
   PE → загрузка CLR → JIT при первом вызове → выполнение с сервисами.
2. `code-blanks` — допиши IL для `Add`.
3. `tap-line` — в дампе метаданных найди сигнатуру `Add`.
4. `rig` — JIT-стенд: вызови методы так, чтобы скомпилировалось ровно 2 из 4.
5. `sort` — JIT / R2R / Native AOT.
6. `rig` — пропускной пункт, 3 карточки.
7. `order` — цепочка хоста.
8. …6 смешанных `choice` / `predict` / `match`, включая по одной ловушке из
   каждого уровня.
9. `speed` — финальный раунд 30 секунд.

Награда: +100, наклейка **«BYTE PATH»** на картридж .NET, анимация: весь путь на

## 8. Тесты (что обязательно проверяется)

**Движок**
- `run.js`: верный/неверный ответ меняет жизни и очки по таблице; 0 жизней даёт
  `gameover`; ошибки попадают в разбор; `1UP` не поднимает жизни выше 3; при
  одном seed порядок одинаковый.
- `check.js`: на каждый тип карточки — верный ответ, неверный, частично верный
  (`multi`, `sort`, `order`).
- `score.js`: звёзды по числу ошибок; комбо `speed`.
- `progress.js`: серия растёт на следующий день, сгорает через день; повреждённый
  JSON и недоступный `localStorage` не роняют страницу.

**Контент** (на каждый уровень трека, автоматически)
- у каждой карточки известный тип и ответ, который проходит свою же проверку;
- у каждого **неверного** варианта `choice`/`multi` есть объяснение;
- все ключи текстов есть в словаре на обоих языках; текст `intro` ≤ 40 слов;
- в уровне 9–14 карточек, ID уровней уникальны, порядок в `track.js` совпадает
  с файлами;
- каждая плашка «Сверено с докой» ссылается на запись в `facts.js`.

**Модели стендов**
- стековая машина: `ldarg.0 ldarg.1 add ret` при (40, 2) даёт 42; `a*b+c`
  считается верно; `ldarg.0 add ret` даёт `underflow`;
- JIT: повторный вызов не компилирует заново; невызванный метод не
  скомпилирован; с `TIERED` метод компилируется второй раз после порога;
- пропускной пункт: у каждой карточки задан правильный вердикт, есть ровно одна
  «ловушка»;
- хост: только правильный порядок доходит до `Main`.

## 9. Критерии готовности MVP

- [ ] С главной есть вход в аркаду; зал показывает картридж .NET и минимум два
      `COMING SOON`.
- [ ] Карта трека .NET: мир 1 из 8 уровней и босса, уровни открываются по порядку.
- [ ] Все 9 уровней проходятся от начала до экрана итогов на телефоне (360px) и
      десктопе, мышью, тачем и клавиатурой.
- [ ] Жизни, разбор ошибок, `1UP`, `GAME OVER`, звёзды, очки, серия, наклейки
      работают и переживают перезагрузку страницы.
- [ ] EN/RU переключаются на лету, включая открытый уровень.
- [ ] `prefers-reduced-motion` убирает вспышки и тряску; звук по умолчанию
      выключен.
- [ ] Все факты «Сверено с докой» сверены с learn.microsoft.com, ссылки в
      `facts.js`.
- [ ] `npm test` зелёный, `npm run stamp` выполнен, README дополнен разделом
      про аркаду.

## 11. Открытые вопросы

1. **Название полки.** Предлагаю `ARCADE` / «Аркада». Альтернативы: `ACADEMY`,
   `GAME ROOM`, «Игровой зал».
2. **Жизни.** 3 на попытку уровня без восстановления по времени (предложено)
   или общий запас в духе Duolingo? Второй вариант раздражает и для учебного
   сайта не нужен.
3. **Язык интерфейса уроков.** Как на всём сайте: EN по умолчанию, RU
   переключателем? Или для аркады по умолчанию RU?
4. **Порог «перепрохождения».** Давать очки за повторное прохождение уже
   пройденного уровня (меньше, например +5) или только за улучшение звёзд?
5. **Глубина «Сверено с докой».** Только короткие плашки (предложено) или
   отдельный необязательный уровень 1-9 «Современный .NET: tiered, PGO, хост»?
